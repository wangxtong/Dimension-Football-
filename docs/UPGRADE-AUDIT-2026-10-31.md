## 8 个角色和总控工作方式

| 角色 | 已实现的职责 | 总控继续关注的方向 |
| --- | --- | --- |
| A1 总控架构与集成 | 接口契约、独立工作树集成、生产网页恢复、证据台账 | 以网站实际回读和服务重启结果决定上线，不按提交数量计完成率 |
| A2 来源可靠性 | 来源冷却、预算、robots、分联赛降级 | 核验真实可用覆盖和缓存年龄，逐源观察失败与恢复 |
| A3 数据身份与编排 | 球队 ID、来源赛事修订、历史缓存、可重放输入、四类调度入口 | 同源历史匹配和改期处理，避免旧赛程被当作新观察 |
| A4 预测评估 | 提前量回放、样本质量、预测和赛果账本 | 增加真实前瞻样本，按联赛与提前量评估后再讨论校准 |
| A5 严格盘口 | 最新快照替代、不可用市场、初盘绑定、冲突与摘要 | 第二来源和真实初盘未满足时保持具体阻断 |
| A6 发布通知 | 网站读回、归档独立状态、持久通知 outbox | 同版本读回后才接受网站发布；防止 ECS/Actions 双重通知 |
| A7 ECS 运维 | 可核验打包、调度、健康、备份、恢复、回滚 | 在现有 Nginx 中仅新增专用路径，保留旧服务，实机演练 |
| A8 网站与质量 | 完整校验、刷新行为、数据提示、真实浏览器验收 | 发布包与页面协议同步，防止不可消费报告替换最后正常版本 |

`collector/control.mjs` 维护修复任务账本，状态为 pending、active、review、verified、blocked。verified 要求当前提交对应、最近的成功验收文件及摘要；blocked 要写明依赖。`collector/operations.mjs` 和独立健康定时器每分钟检查状态、磁盘、任务结果和真实报告链路，并记录修复方向。这是确定性的运维监控，不是后台长期运行的 8 个语言模型，也不承诺无人值守自动改代码。

## 生产架构和更新频率

访客仍使用原 Sites 看板和现有应用登录。ECS 保存真实数据和状态，通过 Nginx 的 `/dimension-football/` HTTPS 命名空间提供机器授权报告；本地报告服务只监听 `127.0.0.1:8787`。保留现有 8000 网站和 8091 消息桥，不复用旧消息桥机器人的凭证或收件目标。

一分钟调度器轮询到期任务；默认赛程间隔 15 分钟、盘口检查间隔 2 分钟、发布检查间隔 1 分钟、赛果检查间隔 1 小时。单进程锁和任务预算避免重叠；每次只执行一个到期任务，实际间隔受任务耗时、来源冷却和服务状态影响。没有未来 24 小时目标比赛时跳过盘口采集。所有报价继续按真实观察时间判断有效期。

GitHub Actions 保留测试与归档/灾备职责；ECS 完成验收后作为唯一生产发布与通知执行者。Actions cache 不是持久业务数据库。归档成功、网站可读取、通知平台接收和回执同步分别记录。

## 必须继续完成的实机验收

1. 使用已核验提交的部署包和独立 SHA256，在 Workbench 安装；先备份并核验现有 Nginx，新增命名空间后执行 `nginx -t`，失败恢复。
2. 将独立报告读取令牌和机器探针令牌配置到 Sites；秘密不写进源码、压缩包或聊天明文。Telegram 继续使用用户指定的新机器人和已核对的目标群。
3. 触发完整真实采集，要求 ECS 报告、Sites `/api/report` 和探针返回同一 reportId/摘要，数据模式为 `ecs`，再记录网站 published。
4. 对同一报告重复执行发布，确认网站不回退且不重复发送 Telegram；检查 API 接收回执，不能声称用户已读。
5. 重启采集与报告服务，确认初盘、冷却、预测账本、当前版本与 outbox 都保留。检查一个小时的调度、时效和错误恢复。
6. 在临时目录演练备份恢复，核对版本和状态兼容后保留可回滚版本。

剩余限制：共享登录限速仍为 Worker 单实例内限速；未实施全局共享限速。尚未取得满足完整语义的第二独立盘口源与真实初盘。以上限制应继续保留在台账中，不以新增页面或候选数量作为修复完成证据。
